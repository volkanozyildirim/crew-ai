# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

CrewAI-based agentic Agile SDLC pipeline. Takes an Azure DevOps Work Item ID and autonomously runs 13 steps from requirements analysis through PR creation, review, test planning and UAT. Two run modes: long-lived FastAPI server with a MySQL job queue and a live dashboard, or one-shot CLI.

**Prompt language convention (as of 2026-04-21):** agent system prompts and task instructions in `config/agents.yaml` and `config/tasks.yaml` are in **English** for reliable LLM instruction-following (especially for smaller local models like Qwen3:8b / Qwen2.5-coder:7b). The work item content (title, description, AC) is read as-is (Turkish). **User-facing output** — markdown headings in expected_output, JSON `desc`/`summary`/`description` field values, WI comments, log messages, dashboard text — MUST remain in Turkish. When editing these YAMLs: write rules/workflow/checklists in English; preserve Turkish in the expected_output templates and instruct the agent to write text fields in Turkish.

## Common commands

```bash
# Install (editable, in a venv)
python -m venv .venv && source .venv/bin/activate
pip install -e .

# CLI: one-shot run for a WI
agile_sdlc_crew 12345           # equivalent: python -m agile_sdlc_crew.main 12345
agile_sdlc_crew 12345 --hal     # use HAL planning path instead of CrewAI

# Server: queue + dashboard at http://localhost:8765
./start.sh                       # spawns server, logs to /tmp/crew_server.log
serve                            # foreground (project script)

# Queue a job via API
curl -s -X POST http://localhost:8765/api/run \
  -H 'Content-Type: application/json' \
  -d '{"work_item_id":"12345","use_hal":false}'

# CrewAI scaffolding entry points (rarely used; pinned to analysis_crew only)
train 3 training_data.pkl
replay <task_id>
test_crew 2
```

There is no test suite, linter, or formatter wired up. Don't invent a `pytest` / `ruff` invocation — verify changes by importing modules in the venv (`.venv/bin/python -c "from agile_sdlc_crew.server import app"`) or running an end-to-end pipeline against a WI.

## Logs to read when something fails

- `/tmp/crew_server.log` — full stdout/stderr of the server process (CrewAI verbose output, LLM call panels, tracebacks)
- `/tmp/crew_pipeline.log` — pipeline-only log (rotated, 10 MB × 5)
- `/tmp/crew_access.log` — uvicorn HTTP access log
- `src/agile_sdlc_crew/web/status.json` — current job's per-agent + per-step state, written by `dashboard.StatusTracker`

The dashboard polls `status.json` every 2s; `/api/status` reads the same file.

## Architecture

### Orchestration: `flow.py` (CrewAI Flow)

`AgileSDLCFlow` is the single source of truth for the 13-step pipeline. It uses CrewAI Flow's `@start`, `@listen`, `@router`, `and_`, `or_` decorators to declare an event-driven DAG. The flow holds pydantic state (`AgileSDLCFlowState`) plus private attrs for `_client`, `_repo_mgr`, `_vector_store`, `_agile_crew`, `_tracker`, `_db`. Steps:

```
initialize ─► [router] ─► hal_planning            (─► step5)
                       └► crew_step1_requirements ─► step0_kickoff_meeting
                          ─► crew_step4_technical_design ─► step5_create_branch
                          ─► step6_implement_code ─► step7_create_pr
                          ─► step8_code_review ─► pr_build_gate ─► (and_) step9_test_planning + step10_uat
                          ─► step11_completion_report
```

Each step calls `self._step_start/_step_done/_step_fail/_resume_step` to update both the dashboard tracker and the MySQL `job_steps` table. Resume (`CREW_ENABLE_RESUME`, default **false**): `_try_resume_step` reuses a step's completed output from a PRIOR job of the same WI — it is **step-level**, so completed steps of a *failed* job are reused too (`get_cached_step_output` prefers fully-completed jobs via `ORDER BY (j.status='completed') DESC`). Only `requirements_analysis_task` + `kickoff_meeting_task` actually call it. `run_pipeline()` in `main.py` is a thin wrapper that constructs the flow and calls `flow.kickoff(...)`.

### LLM selection: `llm/` package + `config/llm_profiles.yaml`

LLM choice goes through a 3-layer registry/profile system instead of inline if/elif.

- **Providers** (`llm/providers/*_provider.py`) — each is a `build(model, max_tokens, **kw) -> crewai.LLM` factory registered by name in `llm/registry.py`. Built-in: `litellm`, `anthropic`, `claude_cli`, `ollama`, `lmstudio`. Adding a new backend = one module + one line in `_bootstrap_builtin_providers`.
- **Profiles** (`config/llm_profiles.yaml`) — named `{provider, model, max_tokens, ...}` bundles like `architect_premium`, `developer_cli`, `developer_local_coder`, `reasoning_local`. Profiles are the unit of reuse; agents bind to profiles, not to providers directly.
- **Resolver** (`llm/resolver.py`) — `build_for_agent(agent_key)` resolves in this order: (1) `CREW_LLM_PROFILE_<AGENT_UPPER>` env override → (2) `llm_profile:` field in `agents.yaml` → (3) backwards-compat from `CREW_USE_LOCAL_LLM` / `CREW_LOCAL_DEVELOPER` → (4) `agent_defaults` map in profiles yaml.

The `LLM_ARCHITECT / LLM_DEVELOPER / ...` lambdas in `crew.py` are now thin `build_for_agent("software_architect")` calls. `_create_llm` and `_create_local_llm` remain as backward-compat wrappers (still used inline in `crew.py` for ad-hoc LLM creation in `create_kickoff_crew` etc.) — both delegate to the registry.

Loadbearing rules baked into the resolver and profiles:
- Architect default is **always** premium remote (`architect_premium` = `vertex_ai/claude-sonnet-4-6`). `CREW_USE_LOCAL_LLM=1` does *not* downgrade architect — explicit per-agent env or `llm_profile:` is required.
- Developer downgrades to `developer_local_coder` (qwen2.5-coder:7b) only when both `CREW_USE_LOCAL_LLM=1` and `CREW_LOCAL_DEVELOPER!=0`.
- Kickoff (step0): the active `run_kickoff_meeting` path uses `_build_kickoff_agents` → `build_for_agent(...)` → dashboard `config/agent_llm_overrides.yaml`. It is **NOT** local Ollama. (The legacy `create_kickoff_crew` is unused.) Its architect and developer bind to the *kickoff* keys below, not to the pipeline ones.
- **Grunt vs decision split** — an agent's cheap phases have their own `agent_key`, so the model is chosen per *phase*, not per persona: `software_architect_explore` (Faz A repo scan), `software_architect_kickoff`, `senior_developer_kickoff` → `architect_explore_cli` / `kickoff_cli` (sonnet) via `agent_defaults`. The persona still comes from `software_architect` / `senior_developer` in `agents.yaml` — only the LLM differs. **The decision points stay premium and must not be moved onto these keys**: `_architect_emit_json` and `_amend_plan` write the plan, `create_code_crew` writes the code, `code_reviewer` is the gate. `create_analysis_crew_toolless(agent_key=...)` defaults to `software_architect`, so any call that does not opt in keeps the old behaviour. The keys are deliberately absent from `agent_llm_overrides.yaml` (that file is the human/dashboard layer) and are excluded from the `CREW_USE_LOCAL_LLM` fallback in `_backwards_compat_profile` — exploration is 15+ turns of native `Read`/`Grep`/`Glob` tool use, which a local 8B model does badly and would silently return an empty scan. They are registered in `server._AGENT_KEYS` and in `assert_models_reachable` because unregistered config drifts silently. Rollback is one env var: `CREW_LLM_PROFILE_SOFTWARE_ARCHITECT_EXPLORE=architect_cli`. Measured basis: exploration was 29 calls / **43%** of `technical_design_task` ($34.40 of $80.60, $1.19 per call).
- **`CREW_CLI_CALL_MAX_USD` destroys the work it interrupts.** The knob appends `claude --max-budget-usd` to every repo-tool (`--add-dir`) call. Its schema default is `0.0` but the **effective value is 1.5**, so it is live. Probed 2026-09-21: when the cap fires the result event is `is_error: true`, `subtype: error_max_budget_usd`, `result` is **empty**, and the stream carries only `tool_use` blocks (no `text`), so `_run_streaming`'s salvage recovers **nothing** — the money is spent and the exploration is lost. The cap also overshoots (a $0.04 cap billed $0.078). It is therefore *not* a graceful truncation and must not be treated as one; to cut exploration cost, reduce turns or the prefix instead. The interruption is now visible: `claude_cli_llm` records the result `subtype` into `meta["stop_reason"]`, logs a distinct `💸 BÜTÇE CAP'İ KESTİ` warning (the generic error line printed an *empty* message, which is why this stayed invisible), `db.record_llm_call` persists it in `llm_calls.stop_reason`, and `cost_analytics` raises a separate finding with the wasted amount. 11 historical calls sit at or above $1.50 totalling $18.26 — those predate the column, so they read as 0.
- **Faz A findings are reused across amend rounds.** `crew_step4_technical_design` stores the exploration output in `_architect_findings` (capped at `_FINDINGS_REUSE_MAX`) and `_amend_plan` injects it as a "do not repeat" block. Measured: 6 jobs scanned the same repo 2–3 times and the extra scans were **15%** of `technical_design_task` ($11.78 of $80.60). Repo tool access stays **on** in amend — the feedback can point at a file the first scan never opened, so the win comes from not re-discovering, not from cutting access.
- **Placeholder order in `tasks.yaml` buys nothing on the claude_cli path — the lever is prompt SIZE.** `{previous_context}` comes **before** `{scrum_master_feedback}` in the five tasks that carry both (`requirements_analysis_task`, `technical_design_task`, `review_pr_task`, `test_planning_task`, `uat_task`), and `test_prompt_prefix_order` locks it — keep it, it is correct for a real prefix cache and harmless here. But the original rationale ("a second attempt re-*reads* the prefix instead of re-*writing* it") was **wrong for `claude -p`** and must not be used to justify further prompt surgery. Probed 2026-09-24 with three back-to-back calls carrying an 80K-char (~20K token) identical context: a **byte-identical** repeat read 72,036 / wrote 0 ($0.2882 → $0.0145, **20× cheaper**), but changing only the **last ~90 characters** read just 7,361 and rewrote **64,673 — 90% of the prefix** — scoring exactly like a control call with a completely different context. So `claude -p` places cache breakpoints only after **[system prompt + tool definitions]**; the **entire user message is one atomic cache block**, and one changed byte anywhere in it invalidates all of it. There is no partial reuse to order for. This also re-reads the old measurement: the 14.8K "read" per Faz-B call was never a surviving prefix, it was the system block (an agent's persona + injected `knowledge/` runs 12–21K tokens and *is* cached correctly), and the 20.4K "written" was the whole user message, every single time. Consequences: (1) for the 445 single-turn calls (read/write **0.62**, $108 of $216) the user message is written at cache-write price and never read back, so **every KB removed is a linear saving** — this is what makes `focused_source`-style diff-windowing (measured 58–62% smaller context with *better* coverage) a cost AND quality win; (2) the 127 multi-turn calls (read/write **9.31**) are the efficient half — their turns re-read a cached session, so **cutting turns is the wrong lever**; (3) the one 20× win available is making repeated calls **byte-identical**, which is worth engineering for wherever a step issues the same prompt twice.
- **Why exploration is expensive — turns, not context.** A row in `llm_calls` is one `claude -p` *session*, so its token counts are summed over every turn. The 29 exploration calls: fresh input 161K (0.8%), cache **write** 1.42M (7.2%), cache **read** 18.2M (**92%**), across 450 turns (15.5 per call). That is **~44K per turn, ~40K of it cache read** — the real per-request context is ordinary, nowhere near any model's window. The cost is a ~44K prefix re-read on all 15.5 turns. So the levers are **fewer turns** or **a smaller prefix**, not a bigger-context model — and the same arithmetic explains the 3.8 cache read/write ratio the Maliyet tab reports.

`crew.py` monkey-patches `litellm.completion` near the top to strip the trailing assistant message (Vertex Claude doesn't support prefill) and disables SSL verification globally for httpx. Leave both alone unless you understand why.

### claude_cli gotcha: the tool bridge is broken

CrewAI's Python tools (`browse_repo`, `search_code`, `AzureDevOpsBrowseRepoTool`) **never reach** claude_cli agents. `claude -p` is a self-contained Claude Code agent with its own sandbox tools; CrewAI's ReAct tool-execution loop can't bridge into the subprocess, so agents say "tools not available/invokable" and hallucinate blindly (this caused the wrong-repo + new-file bugs). Mitigations: (a) **pre-fetch** file contents in Python into the prompt context (the `_prefetch_*` patterns); (b) `CREW_CLI_REPO_TOOLS=1` → `claude_cli_llm.set_repo_ctx`/`repo_tools_context` passes `--add-dir <clone> --allowedTools Read,Grep,Glob,LS` so the agent explores the real cloned repo with its native tools (and may edit in place → the pipeline reads the edited file from disk via `_prefer_worktree_edit`, then restores the worktree). Repos are FULL clones under `~/.crew_repos/<repo>`. Also: claude_cli reports **0 tokens** to CrewAI — see Cost guard.

**The repo context must cross threads.** `set_repo_ctx` / `set_toolless` used to be `threading.local`, but crewai runs a crew's LLM call on a *different* thread than the flow step (`asyncio.to_thread` → `asyncio_0`, probed). The call saw no `--add-dir`, and since `CREW_CLI_AUTO_TOOLLESS` that meant `--disallowedTools` — Faz A exploration (and the implement step's `Edit,Write`) ran with **no file tools at all**. Measured: the last tool-using architect exploration in `llm_calls` is job #186 (2026-09-09, 18–20 turns); jobs #225–#227 (2026-10-16) explored in **one turn** and answered `INSUFFICIENT: … no Read/Grep available`, ending `needs_info`. Both are now **`ContextVar`s**: `asyncio.to_thread` and crewai's own thread spawns copy contextvars, so the context reaches the call thread — but only that step's: a concurrent job (e.g. `pr_review`) or a later step never sees it. Do not replace this with a process-wide fallback (that was tried and leaks one job's `--add-dir` + `Edit,Write` into another job's calls). `test_repo_ctx_cross_thread` locks both directions.

### Work item / SCM provider abstraction: `providers/`

`providers/factory.py` returns singleton `WorkItemProvider` and `SCMProvider` based on `CREW_WORK_ITEM_PROVIDER` and `CREW_SCM_PROVIDER`. Only `azure_devops` is implemented today; jira/github/gitlab/etc. raise `NotImplementedError` from the factory. Add a new provider by implementing `providers/base.py` interfaces and registering in the factory — don't add provider-specific code to `flow.py` or `crew.py`. Most existing call sites still go through `tools/azure_devops_base.AzureDevOpsClient` directly; treat the providers package as the migration target.

### Server, queue, persistence

- `server.py` — FastAPI app. Endpoints: `/api/run` (queue), `/api/pr-fix` (run `pr_fix.run_pr_fix` in a thread), `/api/jobs[/{id}]`, `/api/jobs/{id}/retry`, `/api/status`, `/api/health`. A single background worker thread (`_ensure_worker`) drains the queue serially.
- `db.py` — MySQL via pymysql. Tables `jobs` and `job_steps` (schema in `SCHEMA` constant, auto-created). `STEP_DEFINITIONS` is the canonical step list and order; keep it in sync with the flow when adding/removing steps.
- `dashboard.py` — `StatusTracker` writes `web/status.json`; `start_dashboard_server` is the legacy stdlib HTTP server used by the CLI path. The FastAPI server in `server.py` is the production path.

### Embedding selection: `embed/` package + `config/embed_config.yaml`

Mirrors the LLM registry. Providers (`embed/providers/*`): `fastembed`, `ollama`, `openai`. Resolver (`embed/resolver.py`) precedence: `config/embed_config.yaml` (written by the dashboard) → `CREW_EMBED_PROVIDER/MODEL/BASE_URL` env → provider default (`fastembed` + `BAAI/bge-small-en-v1.5`). Runtime default in use today is `fastembed` / `intfloat/multilingual-e5-large` (1024-dim, multilingual for Turkish content). No LLM is involved — text is embedded directly. **Gotcha:** changing the model/dim auto-resets the LanceDB table (`_reset_table_if_dim_mismatch`) — old vectors are dropped, not migrated.

### Tools (CrewAI tools the agents call)

In `tools/`. The Azure DevOps tools share `AzureDevOpsClient` (`azure_devops_base.py`); `local_repo.LocalRepoManager` clones repos under `CREW_REPOS_DIR` (default `~/.crew_repos`) and is the tool layer's git interface; `vector_store.VectorStore` embeds `REPO_SUMMARY.md` (and targeted plan-file code chunks) into a local LanceDB at `CREW_VECTOR_DB`; retrieval is hybrid — `bm25_search.HybridSearcher` fuses BM25 lexical hits with vector results (`CREW_HYBRID_SEARCH`, default on) so exact identifiers/paths rank well. Agent-facing search tools: `semantic_search`, `find_relevant_repos`. `tool_cache.py` deduplicates repeated tool calls within a single pipeline run (reset in `initialize`). `claude_cli_llm.py` is the litellm custom provider implementation, not a tool agents call.

### Cost guard

`flow.py` calls `_track_and_check_budget` after each crew kickoff (limit `CREW_MAX_JOB_COST`, default 3.0). **claude_cli reports 0 tokens to CrewAI**, so the token×price approximation (`CREW_PRICE_*`) is ~0 — real cost comes from the `claude -p` result JSON (`total_cost_usd` + `usage` tokens). Every claude call is recorded via the `claude_cli_llm` sink into the `llm_calls` table + denormalized `jobs`/`job_steps` totals (per-agent breakdown: `db.get_job_cost_summary`); the guard uses `max(token_approx, real)`. **Mid-step cap**: since the guard only runs at step boundaries and kickoff is one step with ~37 calls, the sink calls `claude_cli_llm.signal_budget_exceeded()` once the running total passes the limit → subsequent claude calls short-circuit (return "") so overshoot is ~1 call, not 2×+.

### PR build/test gate

`pr_build_gate` (env `CREW_PR_BUILD_GATE`) runs between `step8_code_review` and step9/step10. Azure DevOps runs a `<repo>-test` build on every PR (`refs/pull/{id}/merge`); the gate polls `AzureDevOpsClient.get_pr_build`, and if tests fail loops the developer to fix them (source + test files) until green (`CREW_PR_BUILD_MAX_RETRIES`). No pipeline on the repo → gate is skipped. `CREW_REQUIRE_TESTS` makes the architect include test files in the plan and the reviewer reject PRs missing test coverage.

### Branding & dashboard shell

Product name is **Tempo** (tagline "Sprintin ritmi"); constants live in `branding.py` (`PRODUCT_NAME`, `PRODUCT_SIGNATURE`, `is_bot_comment`). WI/PR comment signatures are `*Tempo …*`; `is_bot_comment` still recognises the legacy `Agile SDLC Crew` marker so old bot comments are filtered correctly. The Python package name `agile_sdlc_crew`, step keys and `CREW_*` env vars are unchanged.

`web/index.html` (single file) is organised as top-bar tabs — **Genel bakış** (running job hero with the 13-step strip from `/api/jobs/{id}`, human-waiting list, sprint card, team from `status.json` agents, activity log), **Board** (kanban; WI cards carry a 13-segment pipeline strip via `wiPipelineBadge`), **İşler** (grouped job list + step timeline detail, side by side), **Retro** (the old `#retroModal` markup moved inline into `#paneRetro`; `openRetro()` and the id are kept because `tests/test_katman0_gates.py` greps for them). Theme tokens are CSS variables on `:root` (light) with dark under `prefers-color-scheme` and `data-theme`; `toggleTheme()` cycles system → light → dark (`localStorage.tempo_theme`). Keep the old variable names (`--bg-card`, `--accent-light`, `--text-dim`, …) — the settings/kickoff modals depend on them. Fonts: Geist + Geist Mono; no emoji in shell chrome (inline SVG icons).

## Notes for editing

- All step keys (e.g. `kickoff_meeting_task`) are stable identifiers used in `tasks.yaml`, `STEP_DEFINITIONS`, `dashboard.TASK_DISPLAY_NAMES`, MySQL, and `status.json` — renaming one means renaming everywhere.
- New pipeline behaviors should be env-toggleable (existing pattern: `CREW_KICKOFF_MEETING`, `CREW_SM_REVIEW`, `CREW_ANALYZE_WI_MEDIA`). Default to off if there's any cost or risk impact.
- `.env` is auto-loaded by `server.py` and `main.py` via python-dotenv from the repo root.
- **Restarting the server orphan-fails any running job** (`db.fail_orphan_running_jobs` runs on startup). Don't restart while a job runs — check `/api/health` shows `running:0` first. (The worker drains the queue serially, one job at a time.)
- `db.py` uses pymysql **DictCursor** — rows are dicts (`row['Field']`, e.g. `SHOW COLUMNS` → `r['Field']`). The `jobs` error column is `error_message`, not `error`.
- **Review verdict**: `step8_code_review` / `_review_retry_loop` decide rejection via `_review_rejected()` — it parses ONLY the `REVIEW_DECISION:` sentinel / the `Verdict:` line, never a whole-text substring. (Whole-text matching caused a false-RED retry loop: the `tasks.yaml` template/rules repeat "CHANGES_REQUIRED".) Keep the sentinel in `review_pr_task` expected_output.
- **`is_bot_comment` has to match the RENDERED signature, not the markdown one.** Azure DevOps takes a comment as markdown and hands it back as HTML: the `*Tempo — Hazırlık Kapısı*` we post comes back as `<em>Tempo — Hazırlık Kapısı</em>` — **the asterisks are gone**. `BOT_COMMENT_MARKERS` carried `"*Tempo"` (with the asterisk), so since the Tempo rebrand **none of our own WI/PR comments were recognised**; only pre-rebrand ones matched, and only because the legacy marker `Agile SDLC Crew` is a bare string. This was harmless while nothing read comments back — then `wi_comments_block` made comments a requirements source and it became a **loop**: the readiness gate's own "these details are missing" comment was counted as a *human* requirement on the next evaluation. Measured on WI #73061: our own 1868-char refusal joined the human set (block 1687 → 3595 chars). `is_bot_comment` now also strips tags and looks for `Tempo —` / `Tempo -` / `Tempo ·` in the **last 400 characters**; the tail restriction is what prevents a human comment that merely mentions the product from being dropped. Keep both paths — the raw markers still catch a comment we posted but Azure has not re-rendered, and the legacy name still matches anywhere.
- **WI comments are a requirements source now** (`flow.wi_comments_block`, `CREW_WI_COMMENTS`, default **on**). The pipeline read the work item only from `fields` (Title / Description / AcceptanceCriteria); comments live on a **separate Azure endpoint** that the flow never called. `get_work_item_comments` existed and was even wired into `AzureDevOpsGetWorkItemTool` — but that is a CrewAI tool, and the tool bridge does not reach claude_cli agents, so it was dead code. Meanwhile the team answers the gaps *in comments*: WI #73061 came back from the readiness gate at **5/100**, then eleven human comments wrote exactly the missing criteria ("noktanın lokasyonu `shipment_cod_allowed`'da değilse kapıda ödeme gösterilmeyecek", "evet, tüm kargolar için geçerli"), the job was re-run ten days later and scored **5/100 again**; WI #73732 had a working staging curl and a scope decision ("Dalli'yi de dahil edebiliriz") that were likewise never seen. The `needs_info` loop simply could not close. Non-bot comments (filtered by `is_bot_comment`, HTML/`&nbsp;` stripped) now go in **chronologically** — scope decisions build on each other, so reversing them loses the meaning — capped by `context_budget.cap("WI_COMMENTS")` (4000). They enter twice: into `crew_step1_requirements`'s ctx **and** into `wi_content_length` so the gate's content floor counts them, and into `_build_step_context`'s `parts` (job-invariant, so the cache prefix stays stable) for kickoff / technical design / implement / review / test / UAT, where the steering usually is. Measured (2026-09-28, dry-run jobs #215/#216, $0.23 each): WI #73061 fields carry 1980 chars and its comments add **+1687**, readiness **5 → 28** with the BA's own raw score at **55**, and the analysis now cites commenters by name, derives 8 acceptance criteria and an `out_of_scope` from the thread. WI #73732 is the counter-case: 459 chars of fields, +723 of comments, and the score moved 10 → **8** — where the comments carry a curl and a scope decision but no criteria, the gate does not invent readiness. It still fails the 60 threshold — correctly: one comment thread asks where 5post's COD parameters come from and never gets an answer, so the gate is now making an *informed* refusal instead of a blind one. Two things this deliberately does not do: the `ac_empty` −15 penalty still fires on the empty AC **field** even when the BA derived criteria from comments, and comments are injected verbatim — a teammate pasted a `Authorization: Basic …` staging header on #73732, which now reaches the model. Default-on is a deviation from "new behaviour defaults off": this repairs a broken loop rather than adding a feature, and rollback is one flag.
- **Cost attribution survives concurrent jobs now.** `claude_cli_llm` binds `(job_id, step_key, agent)` in a thread-local *and* a process-wide fallback, because crewai runs a crew's LLM calls on a different thread than the flow step. That fallback was a **single slot**, and its comment assumed "the worker queue is serial" — true for pipeline jobs, **false for `pr_review`**, which bypasses the queue and runs in its own server thread, so two reviews can overlap. The job that finished first called `clear_call_context()` and wiped the slot for the one still running, whose record then landed with `job_id = NULL`. Measured on 2026-09-24: jobs 213 and 214 started 5s apart, 214 finished first, and **job 213's $0.61 went to an ownerless row** — `jobs.total_cost_usd` stayed 0 and retro/cost-analytics never saw it. Four jobs since 09-21 (202, 205, 208, 213) have zero `llm_calls` rows for the same reason, ~$2.02 unattributed. The fallback is now a registry of *active* contexts keyed by the setting thread: `clear_call_context()` drops only its own entry and re-points the global at the most recent surviving one, and entries whose thread has died are pruned (which is what keeps the original single-job semantics — and the old test — intact). `test_call_context_cross_thread` now replays the 213/214 interleaving. Residual limit, by design: while two jobs are genuinely in flight the global still names the most recent setter, so a call finishing during the overlap can be attributed to the sibling — exact per-job cost needs one job at a time, or context propagation into crewai's worker threads.

Scoring: Sonar `weight × (1 + log10(count))` — log2 would let 300 CSS warnings outrank a single blocker vulnerability; NR `errors × apps`. `secrets:*` messages are never stored; Tasks for secrets and infra errors are `needs-human` and are not queued. **The SP budget and `CREW_QUALITY_MAX_TASKS` apply to automatic work only**; needs-human items are a separate group (top `CREW_QUALITY_HUMAN_MAX`, default 5, by score) that is opened but never counts against the budget — the old shared pool (`CREW_QUALITY_HUMAN_SHARE`, removed) let a 30 SP Sonar take come back as 8 Tasks of which 7 were secret rotations. `cap_note` says when the task cap, not the budget, ended the selection. An optional **project (repo) selection** (`repos`, case-insensitive; `GET /api/quality/projects` lists repos with findings for the source; the card's *Projeler* picker) restricts a preview/take to those repos — excluded ones show as `seçim dışı proje`. `default_deps` caches `gather` for 120 s so picker → preview → take does not refetch New Relic (~40 s); dedup still reads the board fresh. **External text is untrusted**: NR messages/URIs are user-reachable (anyone can hit a URL), so they are masked (`render.mask_secrets`) and cut to 1000 chars on ingest, URI query strings are dropped, the literal `tempo-fp` is defanged (`rank.defang`) so a message cannot forge a dedup line, and the evidence block is framed as data, not instructions, because the description feeds the pipeline agents.
